# 阶段 S17：用独立数据暴露并修复自然语言覆盖缺口

## 为什么做这次评测

v5 曾在同一批合成问题上达到 20/20，但这不能证明换一种日常说法仍然可用。v6 因此改变随机数据种子和问题措辞，冻结题目、Python 独立金标准、数据指纹与文件哈希，再调用真实模型。

## 评测怎样工作

评测使用 50,000 笔合成订单，包含退款事件、状态、活动归因和未归因样本。金标准由独立 Python 聚合源数据生成，不读取生产 SQL 的结果，也不采用模型答案。模型只能选择语义目录中的指标并给出结构化计划；SQL 仍由模板编译器生成，数据库以只读方式执行，之后由独立 verifier 复核。

每个 API 调用先按峰值单价保留费用。评测限制每请求 2,000 输入 token、1,024 输出 token，最多 50 次请求，预算上限 `$0.10`。本次实际进行了 33 次请求，估算 `$0.0301068`，低于上限。估算不是服务商账单。

## v6 发现了什么

严格通过 14/20；可回答题只有 6/11。X01、X02、X05、X06、X11 都在调用模型前因指标检索找不到候选而澄清；六个失败题中的 X19 还暴露注入措辞覆盖不足。模型没有机会处理前五种表达，所以不能把它们归因于模型计划或 SQL。

消融结果同样有信息量：关闭语义指标检索时 9/20，关闭独立核验时 8/20。模型执行和核验提供了增益，但流程仍受前置词法召回限制。v6 是失败诊断证据，不能用来宣传稳定覆盖。

## 修复内容

1. 为订单比例、金额比例、退款处理结果、支付与退款订单数、退款事件日期补充常见说法匹配。
2. 为按订单创建日期逐日汇总这类未支持请求增加范围检测。
3. 扩展注入短语拒答规则，避免请求改写后落入普通澄清。
4. 加入确定性回归测试，并冻结全新 v7 种子和题目。

先运行 `python -m unittest discover -s tests -v`。再生成数据和独立答案，最后运行 `python -m insightpilot.enterprise_evaluate`。v7 的题集与 v6 不同；只有 v7 结果可用于检查这些修复能否泛化到新题。

## 本阶段边界

v6 是单次、20 题、刻意覆盖边界条件的合成评测，不是线上业务样本，也不证明自然语言覆盖率。v7 即使通过，也只扩大了合成证据。简历不能写成“准确率 70%”而不交代题集与测试边界，更不能写成生产指标。
