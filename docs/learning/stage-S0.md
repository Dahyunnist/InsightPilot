# S0 学习记录：先定业务事实，再谈 Agent

## 本阶段问题与业务影响

“退款率”至少可以指退款订单数占订单数、退款金额占实付金额，或按退款事件统计的比例。若系统自行选口径，可能把品类排错序，令运营团队错误调整预算或商品策略。因此，S0 将指标公式、时间归属、退款状态和零分母规则冻结在产品契约与黄金集里。

## 数据与状态流

`data/seed.py` 中固定的商品、订单和退款记录 → `create_database()` 重建 SQLite 文件 → `data_meta` 写入版本与 UTC 时区 → 测试读取固定数据库 → 人工核算结果与 `evals/cases.jsonl` 的预期值对照。S0 没有模型或 Agent 状态；澄清/拒绝案例的预期状态是后续 Agent 必须遵循的契约。

关键文件：

- `docs/product-contract.md`：场景、指标公式、边界与业务危害。
- `docs/data-dictionary.md`：表粒度、字段、单位和枚举。
- `data/seed.py`：30 个订单、32 条退款和 3 个品类组成的可重建夹具。
- `evals/cases.jsonl`：12 个正常案例、2 个澄清案例、2 个拒绝案例。
- `tests/test_s0_fixture.py`：固定版本/行数、两道手算题、澄清/拒绝契约断言。

夹具用手写固定记录，不用随机数，因此不存在随机种子或每次抽样变化。这样小型黄金集能逐行审阅，也便于人工推导答案。

## 设计取舍

- 一单可有多条退款记录，所以退款表粒度设为“一次退款”；退款订单数必须去重。
- 金额以整数分保存，避免浮点误差；展示元和比例由上层处理。
- 时间全用 UTC 半开区间 `[start, end)`，避免相邻周期重复计入边界。
- 固定小数据优先覆盖容易出错的反例，不模拟真实分布或宣称企业级代表性。
- S0 暂不做 Agent、SQL 防护和 API；本阶段只冻结业务契约和可验证事实。

## 两条失败链

1. 把退款记录直接连接订单，再用 `SUM(paid_amount_cents)` 做分母 → o02 有两条退款，订单金额重复累计 → 金额退款率被压低 → 运营误以为退款更健康。正确做法是先在订单粒度汇总退款，再分别算退款分子与订单分母。
2. 从存在批准退款的订单中取分母 → 没退款或只有 pending 的已支付订单被漏掉 → 退款率被抬高 → 误判整体表现恶化。分母必须独立覆盖全部符合时间/地区/支付条件的订单。

首轮测试确实复现了第二条：错误核算得 `50,000 / 80,000`。修正为独立分子/分母聚合后，正确值是 `50,000 / 90,000 = 55.5556%`。

## 亲手实验（约 15 分钟）

1. 用 `python data/seed.py` 重建 SQLite（1 分钟）。
2. 用 Python 自带 SQLite 接口，分别查询 `orders` 和 `refunds`：统计 10 月 5–11 日已支付订单数、批准退款订单数与金额（5 分钟）。
3. 对比 `COUNT(*)` 与 `COUNT(DISTINCT order_id)`，观察 o02 的分笔记录会怎样改变结果（3 分钟）。
4. 将查询改为 `refunds.status='pending'`，解释为什么金额不能并入批准退款指标（3 分钟）。
5. 用 `evals/cases.jsonl` 对照 N01、N02、N10，写下每个结果的分子、分母和时间字段（3 分钟）。

检查点：能说明 N01 与 N02 为什么分子、分母不同；能解释 N12 按下单 cohort 统计，而 N07 按退款事件时间统计。

## 面试追问与回答

**问：为什么不能只问模型“退款率怎么算”？**  
答：这是企业业务定义，不是语言常识。订单率、金额率和事件率可能导出不同经营决策；系统必须引用版本化定义，遇到缺失口径先澄清。

**问：为什么分母要和退款分子分开聚合？**  
答：退款表是一单多行。连接后直接累加订单金额会重复；若只从退款表取分母，又会丢掉无退款订单。分子、分母需按各自正确粒度计算，再按维度对齐。

**问：小型手写数据能证明系统准确吗？**  
答：不能证明真实分布或生产准确率。它只验证定义、边界和已知反例；后续需扩大经授权的数据覆盖并报告逐题结果，不能把小样本包装成显著结论。

## 风险与停止点

S0 黄金值由人工核算，当前三条测试只自动覆盖两道数值核对和案例结构。后续阶段可扩充逐题执行断言；目前不运行模型，也不宣称 Agent 具备 SQL 安全能力。阶段已交付；等用户完成实验、提问或明确说“继续”后再进入 S1。
