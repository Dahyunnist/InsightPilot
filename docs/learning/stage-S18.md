# 阶段 S18：独立 v7 复核与失败归因

## 结果

在修复指标改述检索、逐日查询边界和提示注入词面覆盖后，使用新数据种子和新题集复测。严格主流程 19/20；安全与澄清 9/9；预设可回答题 10/11；独立 SQL 核验 10/11。v7 未参与代码调试，题目哈希与 Python 金标准在模型请求前冻结。

唯一严格失败是 X01：“出现过退款的已付款订单”没有限定退款状态。目录只支持批准退款订单率。模型要求确认是否仅统计已批准退款，避免把 pending/rejected 混进指标。金标准把它算作可回答题，严格报告仍记失败。这个差异暴露的是金标准措辞与指标口径不一致，不能藏掉，也不能伪称模型答错。

## 为什么保留 verifier

移除独立 SQL 核验后通过数从 19/20 降至 9/20。该消融说明本任务的完整性依赖独立复算与安全校验。移除语义指标检索后通过数为 14/20，说明目录约束也提供了收益。消融在同一 20 题集运行，存在顺序和单次模型波动，不能当成显著性结论。

## 成本与界限

三组共 43 次 API 请求、44,269 token，峰值价格估算 `$0.0404901`，硬上限 `$0.10`。全是 50,000 笔合成订单。总体 Wilson 95% 区间 `[0.7639, 0.9911]`；可回答题区间 `[0.6226, 0.9838]`。20 道题刻意覆盖已支持功能，不代表线上分布。

## 学习与复现

1. 运行全量测试：`python -m unittest discover -s tests -v`。
2. 按指定随机种子生成 v7 数据库。
3. 运行 v7 builder，重算独立 Python 金标准并核对 manifest 哈希。
4. 执行模型评测，检查主流程、失败轨迹和两组消融。
5. 对每个失败先判断用户口径、金标准和系统支持范围是否一致，再决定代码是否需要修复。

不能仅凭一次 19/20 声称 95% 生产准确率。后续应以真实授权业务样本做脱敏抽样、由业务口径负责人标注，再独立复测。
