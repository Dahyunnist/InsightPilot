# S1 学习记录：最小分析闭环

## 本阶段问题与业务影响

S0 只有口径和固定数据，还不能回答运营问题。S1 补上从自然语言到可复核查询的窄闭环。模型只抽取计划；本地代码验证计划并生成 SQL。这样模型输出格式有波动时，不会直接变成数据库命令。

## 数据与状态流

问题 → 写请求/个人信息前置拒绝 → 指标关键词检索 → LLM 返回 JSON 计划 → 校验指标、日期、分组和过滤 → 本地白名单 SQL 模板编译 → SQLite 只读连接执行参数化 SQL → 返回指标口径、区间、数据版本、SQL、参数和结果。

非成功状态明确分开：

- `clarify`：相对日期、模糊口径、缺少日期或多指标问题。
- `refused`：写入/修改请求或个人信息请求。
- `failed`：规划模型调用失败，或本地查询失败；包含失败阶段。
- `answered`：带完整证据字段的查询结果。

关键文件：

- `insightpilot/metrics.py`：退款指标关键词检索与指标口径。
- `insightpilot/planner.py`：OpenAI-compatible API、JSON 计划解析和字段白名单校验。
- `insightpilot/sql.py`：指标计划到参数化 SQL 模板的编译。
- `insightpilot/runner.py`：SQLite `mode=ro`、`PRAGMA query_only=ON`、100 行上限。
- `insightpilot/agent.py`：阶段状态流、拒绝/澄清/失败/回答封装。
- `insightpilot/cli.py`：命令行入口。
- `tests/test_s1_flow.py`：两条端到端指标链、只读限制、歧义和失败状态。

## 设计取舍

- 用轻量关键词检索指标，不把口径文档全文塞给模型，也不把检索命中当业务事实。真实数字仍来自 SQL。
- 模型只能选候选指标、日期、地区和维度；不生成 SQL。SQL 模板固定表名/字段/函数，过滤值使用绑定参数。
- 日期采用 UTC 左闭右开区间。用户说“到 10 月 11 日”时，计划结束日期转为 10 月 12 日。
- 写/个人信息请求在模型调用前拦截。数据库只读 URI 和 `query_only` 再限制执行边界。
- S1 一次处理一个指标。复合问题要分开问，防止只回答其中一半却显得完整。
- 当前是确定性计划解析加模板 SQL，不是 SQL AST 策略；S2 再做 AST、时间/扫描限制和独立结果复核。

## 两条失败路径

1. API 超时、响应不是 JSON、或模型选了未检索到的指标 → 规划阶段返回 `failed` → 不生成或执行 SQL。测试用 `PlanError("LLM request failed: TimeoutError")` 重现规划失败状态。
2. SQLite 文件缺失、连接失败或 SQL 执行失败 → 查询阶段返回 `failed` → 不输出经营结论。测试用缺失数据库路径重现；另用 `DELETE FROM orders` 证明只读连接拒绝写操作，并确认订单仍为 30 条。

澄清与拒绝属于预期控制流，不是失败：测试确认“上周退款率”在调用模型前停止，写请求和手机号导出请求直接返回拒绝原因。

## 测试复现与真实结果

在项目根目录运行：

```text
python -m unittest discover -s tests -v
python -m insightpilot.cli "2026-10-05 到 2026-10-11 华东金额退款率是多少？"
python -m insightpilot.cli "2026-10-05 到 2026-10-11 各品类批准退款金额贡献度是多少？"
```

本次测试输出：`Ran 10 tests ... OK`。两次 CLI 演示真实调用了 `.env` 配置的兼容 API。

金额退款率实值：分子 50,000 分，分母 90,000 分，比例 `0.5555555556`。回答带有 `insightpilot-s0-v1`、UTC 区间、参数、SQL 和指标定义。

品类贡献实值：家电 20,000/50,000 = 40%；服饰 10,000/50,000 = 20%；食品 20,000/50,000 = 40%。SQL 先按订单聚合批准退款，再独立按品类计算贡献。

## 亲手实验（约 15 分钟）

1. 运行第一条 CLI 示例，找出 `numerator_cents`、`denominator_cents` 和绑定参数（3 分钟）。
2. 把问题改成“退款率是多少？”，观察系统返回 `clarify`，不调用模型猜口径（2 分钟）。
3. 用“2026-10-05 到 2026-10-11 各品类批准退款金额贡献度是多少？”运行第二条示例，手算 40%、20%、40%（4 分钟）。
4. 将分组词改成“按渠道”，运行并检查 `group_value` 与 SQL（3 分钟）。
5. 把日期换成“上周”，再把问题改为“删除订单”，观察澄清/拒绝状态（3 分钟）。

检查点：能说明模型计划不是事实；能从答案中的 SQL 和指标口径复算一个结果；能指出数据库只读设置与 SQL 模板各负责哪层。

## 面试追问与回答

**问：这里的 RAG 做了什么？**  
答：S1 还没有完整 RAG，只按显式业务词检索有限指标定义，并把候选交给模型做计划。检索负责找定义；数据库查询负责给事实。若检索候选不清或问题含糊，系统澄清。

**问：为什么模型不直接生成 SQL？**  
答：自由 SQL 会把提示注入或模型格式错误变成执行风险。S1 让模型只填受限结构化计划，代码只用固定 SQL 模板，地区和日期也通过参数绑定。

**问：只读 URI 和模板 SQL 是否足够安全？**  
答：这是原型的两层基础限制，不是生产级安全证明。S1 缺少 SQL AST 策略、查询耗时/扫描预算、列级授权和攻击面评测；S2 补这些控制并保留数据库只读权限。

## 风险与停止点

当前拒绝规则使用关键词，可能漏掉同义表达。结果行数限制为 100，但没有执行超时或扫描预算。指标检索只支持三个显式指标，不支持退款事件率、复合多指标问题或历史基线比较。S1 已完成；等用户亲手实验、提问或明确说“继续”后再进入 S2。
